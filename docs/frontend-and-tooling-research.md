# Research — is there a free Langflow-like tool for the factory?

Question (2026-09-05): *a free tool like Langflow that can visualise how the agents are
connected, show status of jobs, and offer to edit/improve agents.*

Short answer: **several exist, and none of them fit — for one structural reason.**
But two of your three asks have good free answers, one of which is already installed
on your machine.

---

## 0 · The structural reason Langflow-likes don't fit

In Langflow / Flowise / Dify / n8n, the canvas **is** the source of truth. You build the
agent in their editor; the graph lives in their database; export is a JSON blob.

In your factory the source of truth is **markdown in git**:

- roles are `.md` files with YAML frontmatter (`id`, `kind`, `phase`, `authority`,
  `reads`, `writes`, `handoff_to`)
- artifacts are the only channel between agents
- the playbook is cloned per repo and edited per project

Adopting a canvas tool means giving that up — the playbook stops being the truth and
becomes an export target. It also breaks clone-per-repo: you'd need a Langflow instance
per project, or one instance holding N projects, which is exactly the multi-project
complexity you deliberately excluded.

**So the question isn't "which Langflow clone" — it's "which tool reads my markdown
instead of replacing it".** That reframing is what the rest of this file answers.

---

## 1 · Visualising how agents are connected

### Verdict: build it, don't install it. ~1 hour, zero dependencies.

Your frontmatter is *already* a graph. `handoff_to` is the edge list; `reads`/`writes`
give the artifact edges; `id` is the node key; `phase` gives you swim-lanes. A short
script that walks the `.md` files and emits Mermaid gives you a diagram that:

- renders natively on GitHub, in VS Code, and in Claude artifacts — no server, no build
- is committed, so it version-controls with the playbook and can't drift
- costs nothing per clone, which matters when the playbook is cloned per repo
- can be regenerated in CI so a wrong `handoff_to` target fails the build

That last point is the real prize: the same walker that draws the graph also
**validates** it. `CONTEXT.md` step 4 already lists "verify `reads`/`writes`/`handoff_to`
targets and links resolve" as a manual chore. This automates it.

You already have `process-flow-a3.svg`, which is the hand-drawn version of this. The
generated one stays true.

Tools looked at and rejected for this job:
| Tool | Why not |
| --- | --- |
| Langflow / Flowise / Dify | Canvas owns the definitions (see §0) |
| n8n | Same, plus it's an automation platform — wrong shape entirely |
| Swark | Generates architecture diagrams from *code* via LLM; your agents aren't code |
| Online YAML→Mermaid visualisers | Single-file, manual paste, no frontmatter semantics |
| OpenAI Agents SDK `draw_graph` | Graphviz over *their* SDK objects; you'd have to port |

## 2 · Status of jobs

This splits by **where the run happens**, and that split matters a lot for you.

### 2a · Runs on your machine → you already have it, free and official

**Anthropic Agent View** — `claude agents`. Shipped 2026-05-11, needs v2.1.139+.
**You are on 2.1.261 and I verified the subcommand works on your Mac.**

- A table of every background Claude Code session on the machine, any project/worktree
- Rows grouped by state: **Needs input** and **Ready for review** float to the top,
  then **Working**, then **Completed**
- Each row gets a one-line summary of what the agent is doing / needs / produced,
  generated by a Haiku-class model, refreshed at most every 15s
- Sessions survive closing the terminal — a per-user supervisor process hosts them and
  restarts across auto-updates
- `/bg` backgrounds a running session, `claude --bg` starts one, space peeks at the
  latest turn, Enter attaches to the full transcript

Read that feature list against your `runtime-plan.md` §3 monitor spec — "pipeline board,
live run logs, gate verdicts, twin flags and open PO questions as an inbox". **"Needs
input" is your PO-question inbox. "Ready for review" is your gate queue.** Anthropic
built roughly a third of your dashboard and gave it to you.

**The catch:** it monitors sessions *on this machine*, with state under `~/.claude/`.
Your factory design runs agents in **e2b sandboxes**, so factory runs will not appear
in Agent View. It covers you for local orchestrator development — Phase A/B — and stops
being sufficient the moment work moves off-machine.

### 2b · Runs in sandboxes → Langfuse, but not yet

**Langfuse** (MIT, self-hostable via docker compose) is the strongest free option, and
the reason is architectural: it's **push-based**. The run emits OpenTelemetry traces to
a collector, so it doesn't care whether the agent ran on your Mac, in e2b, or in CI.
Every file-reading tool in §2c fails that test.

- Documented integrations for **Claude Code** and the **Claude Agent SDK**, both via OTel
- Traces every prompt, model response and tool call; dashboards, cost tracking, evals
- Core is MIT; there's a community `claude-code-langfuse-template` for self-hosting

**Why not yet:** Langfuse v3 wants ClickHouse + Postgres + Redis. Your runtime-plan §3
says *"tiny Node server + static SPA, no cloud, no accounts, the repo remains the single
source of truth."* Running a ClickHouse stack per cloned repo contradicts that hard.

Sensible shape if you go there later: **one Langfuse instance for all your projects**
(it's per-machine infrastructure, not per-clone), with the per-repo dashboard linking
into it. That keeps clone-per-repo cheap while giving cross-sandbox visibility.

### 2c · Community Claude Code dashboards — good, but read `~/.claude`

| Project | Stars | License | What it gives you |
| --- | --- | --- | --- |
| `hoangsonww/Claude-Code-Agent-Monitor` | ~973 | MIT | Real-time dashboard, **Kanban status board**, tool usage, subagent orchestration, WebSockets, macOS/Windows apps |
| `Ngxba/claude-code-cli-ui` | ~421 | MIT | **Relationship graph** of agents/commands/skills, visual agent editor, workflow builder, token/cost metrics, terminal emulator. Nuxt 3 + Bun |
| `nyanko3141592/subagent-viewer` | — | — | TUI, real-time subagent activity, 300ms refresh |

`claude-code-cli-ui` is the closest thing to your three asks in one package — graph +
status + edit. Note it needs `bun install` and a dev server, which is friction to repeat
per clone (see §4).

**All of them read `~/.claude/`** — the Claude Code native layer. Which leads to the
decision below.

## 3 · The fork worth sleeping on: adopt `.claude/` or not

Every tool in §2a and §2c reads Claude Code's native subagent format: markdown files in
`.claude/agents/` with frontmatter (`name`, `description`, `tools`, system prompt).

Your playbook uses a **different, richer** schema: `id`, `kind`, `phase`, `authority`,
`reads`, `writes`, `handoff_to`. `CONTEXT.md` lists "the `.claude/` executable layer
(subagents, slash commands, hooks)" as a **parked improvement**.

That parked item is worth more than it looks, because it's the difference between:

- **Adopt `.claude/agents/`** → you inherit Agent View, both community dashboards, the
  subagent TUI, and anything else built on that convention. Free, maintained by others.
  Cost: your schema is richer than theirs. `authority`, `reads`/`writes`, `handoff_to`
  and `phase` have no home in the native format, so you'd either lose them or carry
  both (native file for execution, playbook file for the contract) and keep them in sync
  — which is a new drift surface, and drift is exactly what your convention guard in
  `CONTEXT.md` step 5 exists to prevent.
- **Stay custom** → the schema stays expressive and single-source, and you build your
  own view (§1 gets you the graph half almost free). Cost: no ecosystem.

Not a decision to make tonight, and not one to make on tooling convenience alone — the
`reads`/`writes`/`authority` fields *are* your governance model. Losing them to gain a
dashboard would be a bad trade; carrying both might be an acceptable one.

## 4 · A note on clone-per-repo

Every GUI in §2c needs an install step (`bun install`, `npm install`, a dev server).
Cloned per repo, that's N installs to maintain and N places a fix has to land.

The tools that *don't* suffer this are exactly the ones that are either already global
(`claude agents` — installed once with Claude Code) or generate committed static output
(§1's Mermaid — no runtime at all). That's not a coincidence, and it's a decent rule for
picking factory tooling generally: **per-repo carries content; per-machine carries code.**

---

## 5 · "Offer to edit/improve agents"

The honest answer: **you already have the best tool for this and used it today.**

Editing role docs is markdown editing with judgment — exactly what Claude Code does in
this repo. A visual editor like `claude-code-cli-ui` gives you form fields over
frontmatter; it does not give you "your seven artifact templates declare four different
status vocabularies," which is the kind of improvement that actually matters and which
came out of reading the files.

Where a GUI genuinely helps is *discovery* — seeing the graph and spotting a role with
no inbound `handoff_to`, or an artifact nothing reads. That's §1's generated graph
again, and it's structural, not visual.

## 6 · Recommendation

| Ask | Answer | Effort |
| --- | --- | --- |
| Visualise agent connections | Generate Mermaid from frontmatter; validate targets in the same pass | ~1h, zero deps |
| Status of jobs (local) | `claude agents` — free, official, already installed | 0 |
| Status of jobs (sandboxed) | Langfuse, **one shared instance**, when sandbox runs exist | later |
| Edit/improve agents | Claude Code, as today | 0 |
| Langflow-style canvas | Skip — it would own your definitions | — |

**Do first, before any of it:** unify the artifact `status` vocabulary. Every tool above
renders state it is given. Right now the seven Phase-2 templates declare four different
vocabularies and three declare none, so there is no stage for a board to show. That work
is markdown, it's an hour, and the orchestrator needs it as much as the UI does — it's
how a step reports success, which matters doubly because `claude -p` exits 0 even when
it fails.
